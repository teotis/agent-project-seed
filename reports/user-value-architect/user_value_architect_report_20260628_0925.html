执行建议

Primary bet：把“标准问题解决流程”提升为项目的一等公民：新增一个可初始化、可审计、可归档的 Task Capsule / 问题解决胶囊。它不是更重的项目管理，而是把外部资料、用户问题、分析报告、方案、验证证据、风险和交付物放进同一个稳定对象，删除新环境下最大的路径记忆负担。

主押注：Task Capsule

用户可见时刻：用户把资料放入仓库后，只需运行一个初始化命令或按一个目录约定，就获得本轮问题的入口、证据、报告、验证和交接路径。

结论压缩

  • 最值得做的架构优化不是先加更多目录，而是定义“一个问题解决回合”的稳定对象。当前项目已有 control/、work/、reports 可扩展空间、hooks 和 portable skills，但缺少把它们串成单轮工作流的用户可见结构。
  • 外部热门仓库的启发应变成校准机制，而不是目录仿制。GitHub Copilot coding agent、Codex 的 AGENTS.md 约定、OpenHands/aider 等项目都在强化说明、环境、任务、验证、PR/报告的可追踪性；本项目的差异化应是“轻量但完整的问题解决回路”。
  • 不要让模板从轻量 scaffold 膨胀成 agent 平台。任何新增结构必须能明显降低新用户的 setup、路径选择、证据归档、验证或交接成本。

价值理论

项目特有杠杆

project_seed 的稀缺价值不是“多一个模板仓库”，而是保护用户的 判断力、恢复能力和长期可追踪性。当 agent 参与真实项目，用户最怕的不是少一个目录，而是 agent 把问题理解、证据、风险、实现和验证散落在聊天、临时文件和未提交改动里。

当前独特资产包括：共享 AGENTS.md、统一 control/ledger.md、control/state.md、安全 commit 工具、Codex/Claude hooks、portable user skills、preflight 和 optional complex task live state。最大价值泄漏点是：这些资产还没有在“单轮问题解决流程”上形成一个天然入口。

Leverage thesis：把“任务回合”建成轻量领域对象，会让现有资产成为同一机制的投影：输入材料、分析报告、验证结果、ledger 记录、handoff 都能自然连接。这样才是用户可感知的架构优化。

推荐卡

UVA-01：Task Capsule / 问题解决胶囊

用户可见时刻：用户开始一个真实问题时，不再问“外部资料放哪里、分析报告放哪里、方案和验证怎么关联”。仓库给出一个本轮任务的固定入口和完成出口。

当前体验切片：1. 新项目初始化后有 control/ 与 work/；2. 外部资料可放 work/in，但没有任务级索引；3. 复杂任务可选 tools/project.py task init，但触发条件偏“多包/多 agent”；4. 报告目录不是 scaffold 的正式目录；5. ledger 记录事实，但不天然聚合本轮 evidence、recommendation、validation。

改后体验切片：1. 用户运行或手动创建一个 task capsule；2. 胶囊内有 input、analysis、decision、validation、handoff 的稳定槽位；3. agent 产出报告时自动/明确回链 capsule；4. ledger 只记录 durable facts，细证据留在 capsule；5. handoff 可以从 capsule 回放，不依赖聊天上下文。

结构性价值机制：把“问题解决回合”从散落流程变成稳定对象，删除 setup、上下文重建、证据追踪、完成证明和失败恢复这五类重复负担。

Floor：30%+，因为它直接减少每轮任务的路径决策、归档和交接成本。

Ceiling：2x，若后续和 hooks、status panel、report manifest、validation replay 连接，重度用户的第 N 次任务可显著更快更稳。

Path to ceiling：需要一个小到不会压垮 seed 的对象边界：只收束任务回合，不替代 issue tracker、不变成数据库、不强制所有任务使用。

反证测试：找 3 个真实新任务，让用户只用现有 work/ + ledger 跑；若他们不迷路、交接不丢证据、报告可追踪，则 capsule 价值不足。

拒绝替代：不要直接引入完整项目管理系统或重型 workflow engine；这会破坏 seed 的轻量长期价值。

UVA-02：新环境标准问题解决流程文档切片

用户可见时刻：用户刚复制项目，就能看到一条端到端路径：放资料、让 agent 分析、报告落点、验证、ledger、交接。

当前体验切片：README/SETUP 对初始化、hooks、skills、governance 讲得比较完整，但用户提出的“标准问题解决流程”没有作为 first-class path 出现。

改后体验切片：文档新增一段“Run a problem-solving round”：输入材料放置、推荐报告目录、何时写 ledger、何时创建 task live state、完成回复格式。

处置：这是 small high-certainty improvement，不伪装成 2x 押注；它适合作为 Task Capsule 前的最快验证。

反证测试：如果新用户读完现有 README 已能无歧义跑完整流程，则新增文档只是重复。

UVA-03：外部参照 ledger / radar

用户可见时刻：用户不再担心项目闭门造车，因为每个重大模板能力都能说明借鉴了哪些外部 expectation、哪些只是 parity、哪些 copy risk 被拒绝。

当前体验切片：项目 ledger 记录内部决策，但没有专门表达“外部参照如何影响模板演进”的字段；用户需要临时让 agent 搜索和判断。

改后体验切片：每次架构/流程优化前，可追加一条 external reference record：reference type、user expectation、ceiling signal、copy risk、differentiation path、evidence status。

Floor：30% hypothesis，只对长期演进决策成立；单次任务可见性弱。

Ceiling：3x hypothesis，如果它持续防止项目追逐浅层热门做法，并把优秀外部模式转化为轻量 seed 能力。

反证测试：连续 3 次优化中，外部参照没有改变任何优先级、拒绝项或验证计划，则 radar 只是形式主义。

验证计划

最快学习路径

  1. 选一个真实问题样例：用户提供 2-3 个外部资料文件，要求 agent 分析并给解决方案。
  2. 在不实现完整 capsule 的情况下，先用文档约定手动跑一遍：input、analysis、recommendation、validation、handoff。
  3. 记录迷路点：资料放置、报告路径、ledger 记录粒度、验证命令、最终交付是否需要临时解释。
  4. 若迷路点集中在同一个“任务回合对象”缺失上，再设计最小 Task Capsule。
Pass signal新用户无需额外问路径；agent 交付后能从一个 task capsule 回放证据、决策、验证和风险。
Fail signal用户仍主要靠聊天上下文理解任务状态，或 capsule 只是把已有 control/tasks 换名。
Proxy 风险目录更多、文档更长、报告更漂亮都可能不提升问题解决成功率。必须用回放完整性和路径决策减少来验证。
