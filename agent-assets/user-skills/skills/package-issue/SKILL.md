# Package Issue

## Mission

把异构问题输入转成可审查、可路由的问题包，让用户快速判断：

- 哪些问题必须共同调查、修改或验证；
- 哪些包已经具备继续处理的证据；
- 哪些包仍需设备、日志、账号或人工判断；
- 哪些问题经过核查后值得修复、暂缓、拒绝或需要用户决策；
- 下一步应进入诊断、轻量交接、编排、外部协助还是延期。

默认只做 repo-backed 初查和问题打包；不设计完整修复方案，不生成 DAG、worktree、状态账本或执行脚本，不修改产品代码。

## Invocation Contract

适用于：

- 一次收到多个真机问题、用户反馈、截图、录屏、日志或验收项；
- 用户要求补充问题表现、核查当前实现并形成问题包；
- 多个问题可能共享状态机、布局、媒体管线、能力声明、修改边界或验证矩阵；
- 后续处理方式尚未确定，需要先形成决策清晰的上游输入。

不适用于：

- 单个高难 bug 的深度根因诊断：使用 `diagnosing-bugs`；
- 代码复杂度的全库扫雷：使用 `complexity-sweep`；
- 已有执行任务包且明确需要 DAG、worktree、状态账本、恢复或自动收口：使用 `agent-orchestration-planner`；
- 用户明确要求立即修复：完成必要核查后切换到正常实现流程。

其他 agent 可建议使用，但不得未授权自动串联。

## Investigation Depth

默认使用 `repo-backed`：

- 读取目标仓库指导和 Git 状态；
- 核查相关代码、测试、模块与所有权边界；
- 对照用户提供的截图、日志、录屏和描述；
- 核查到足以形成可靠问题包和 `next_route` 为止。

其他档位：

- `intake-only`：用户明确要求快速整理，或仓库不可用时，只规范化输入并明确证据债务；
- `reproduction-backed`：用户明确要求复现，或高影响争议包必须通过复现才能获得足够判断权限时，增加可重复验证证据。

无论档位如何，都不得把未查看的仓库、设备、日志或媒体写成已核查。

## Evidence Contract

- 为每条证据分配稳定 ID：`EV-001`、`EV-002`。
- Evidence Ledger 至少记录 `type`、`source_artifact`、`observation` 和 `confidence`。
- `confidence` 使用 `observed`、`reproduced`、`measured`、`inferred`、`unverified` 或 `unavailable`。
- 问题包通过 `证据引用` 使用 Evidence ID，不复制或改写原始 observation。
- 图片、视频、日志和用户描述是证据输入，但不能自动证明根因。
- 明确区分观察事实、初步判断、反证或替代解释、未知项。
- 不把旧报告、注释或历史任务包当成当前实现真相。

## Workflow

### 1. Normalize The Intake

保留已有问题编号；没有稳定编号时生成 `ISSUE-001` 等 ID。每项至少提取：

- 原始描述和规范化后的问题表现；
- 期望行为；
- 触发条件、模式、设备或状态；
- 已有证据和缺失证据；
- 初步领域标签。

措辞不清时保留原文，不用推测替换用户原意。

### 2. Establish Current Truth

按默认 `repo-backed` 深度核查：

- 相关模块、所有权和稳定接口；
- 当前 UI、状态机、能力声明或媒体处理路径；
- 邻近测试与验证脚本；
- 已知降级、占位实现或未接线能力；
- 可能共同影响多个问题的共享组件。

核查到足以判断分包边界和下一路由为止；完整修复设计留给下游流程。

### 3. Build The Evidence Ledger

把本轮实际观察到的文件、代码、命令、测试、截图、日志、用户事实、推断和未知项登记为 `EV-*`。主要判断必须能回连到 Evidence ID。

### 4. Assess Fix Worthiness

先核查问题是否值得继续修复，再决定打包和路由。对每个输入问题或候选包记录一个 `修复价值`：

- `fix-now`：用户影响明确，行为与产品目标、验收标准或已承诺能力冲突，证据足以进入修复或交接；
- `worth-fixing-needs-evidence`：问题看起来值得修，但缺少复现、日志、设备、账号、视觉判断或范围证据；
- `needs-user-decision`：是否修复取决于产品取舍、兼容策略、发布节奏、设计偏好或成本上限；
- `defer`：影响较低、证据不足、重复度高、时机不合适或依赖上游变化，当前不应投入修复；
- `no-fix`：核查后确认是预期行为、误报、外部限制、不可支持场景，或修复会破坏更重要的不变量。

核查维度：

- 用户影响：阻塞、误导、数据/隐私/稳定性风险、频率和受影响人群；
- 规范冲突：是否违背用户期望、验收清单、产品承诺、平台规范或当前代码契约；
- 证据强度：观察事实、当前代码、测试、日志、截图、复现和反证是否足够；
- 修复风险：修改边界、回归面、兼容性、验证成本和可回滚性；
- 机会成本：是否符合当前目标，是否会挤占更高价值或更高风险问题。

不得因为“实现难”直接判定不值得修；复杂但高影响的问题可以是 `needs-user-decision` 或 `orchestration`。不得因为证据不足直接判定 `no-fix`；证据不足时应降级为 `worth-fixing-needs-evidence`、`external-assist` 或 `deferred`。所有价值判断必须引用 Evidence ID，并写明反证或替代解释。

### 5. Form Dependency Closures

分包目标是高内聚、低耦合，不追求大小均匀。

以下任一条件成立时，优先吸收到同一个问题包，即使包因此变大：

- 必须共同修改才能保持行为一致；
- 必须共同验证才能判断修复是否成立；
- 共享同一不稳定内部契约、状态机或生命周期；
- 拆开后会产生双向依赖、重复调查或重复回归矩阵；
- 独立落地任一部分会形成不可接受的中间状态。

只有同时满足以下条件时才拆成不同包：

- 包之间通过稳定接口连接；
- 各包可以独立说明用户影响和验收边界；
- 各包可以独立验证、回滚和落地；
- 跨包关系主要是单向执行顺序，而不是共同修复闭包。

跨包依赖必须声明主依赖方向。不要为了限制包大小而切断依赖闭包，也不要因表面相似而强行合包。

### 6. Estimate Complexity

使用相对修改范围，不伪装成精确工时：

| 级别 | 判断 |
|---|---|
| `S` | 单层局部行为或文案/UI 调整，边界清晰，验证简单 |
| `M` | 跨少量组件或状态，需要补测试或设备验证 |
| `L` | 跨 UI、session、device、media 等多层，存在兼容与回归风险 |
| `XL` | 需要重新定义能力、数据模型、媒体格式或长期迁移路径 |

同时给出初查置信度。复杂度不等于优先级，包较大也不代表应继续拆分。

### 7. Assign Next Route

每个包必须选择一个 `next_route`：

- `diagnosing-bugs`：单个高难或偶发问题仍需建立反馈循环和根因证明；
- `handoff`：范围、证据和验证边界清楚，适合单个 agent 或轻量手工任务包；
- `orchestration`：多个问题包存在依赖或并行执行需求，且需要持久状态、恢复、审计或最终收口；
- `external-assist`：需要设备、账号、凭证、审批或人工视觉判断；
- `deferred`：证据不足、价值较低、重复、当前不值得继续或已经判定 `no-fix`。

不得仅因问题数量多或单包较大推荐 `orchestration`。选择它时必须写明具体编排理由。

### 8. Write Decision-First Output

输出前读取 `references/problem-package-contract.md`。报告先给一屏决策摘要，再给输入覆盖、Evidence Ledger、分包总览和问题包详情。

生成文件后运行：

```bash
python3 <skill-dir>/scripts/validate_package_issue_report.py <report.md> \
  --issue-ids CAMERA-BLACK-SCREEN,QA-17
```

校验器只检查结构、覆盖、证据引用和路由，不证明分析结论为真。

## Output Contract

默认输出中文 Markdown。优先使用仓库已有规划目录；没有约定时使用：

```text
docs/plans/package-issue-{YYYYMMDD}.md
```

用户明确要求 chat-only 时不写文件，但仍先给决策摘要，并保留 Evidence ID 和 `next_route`。

## Completion Gate

完成前确认：

- 所有原始问题均被覆盖，已有编号得到保留；
- 默认 repo-backed 核查已覆盖相关代码、测试和模块边界，或明确记录不可用证据；
- 决策摘要能够直接说明包数量、证据缺口、修复价值分布、路由分布和推荐顺序；
- Evidence ID 稳定且所有包只引用已登记证据；
- 事实、判断、反证和未知项已分离；
- 每个包都有修复价值判断，且未把实现困难或证据不足误写为 `no-fix`；
- 分包依据是共享修改或验证闭包，而不是编号、数量或表面相似；
- 拆开的包通过稳定接口连接，并能独立验证、回滚和落地；
- 每个包都有 `next_route`，且 orchestration 具备明确理由；
- 未修改产品代码、Git 历史或无关用户改动。
