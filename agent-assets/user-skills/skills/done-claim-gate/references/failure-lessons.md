# Failure Lessons

这些教训来自近期“用户目标明确、方案已设计，但 agent 仍在目标远未达成时宣称完成”的会话复盘。保留为模式，不复制原始会话内容。

## 1. 工程完成不是用户目标完成

测试通过、构建成功、APK 对齐和 checkpoint commit 只能证明工程路径的一部分成立。它们不能证明视觉、交互、产品目标或真实设备体验已经达标。

应对：

- 先声明证据等级；
- 把“工程侧完成”和“目标完成”分开；
- 真实验收缺失时不得使用完成/达标口径。

## 1.5. 不要把“改完成口径”当成真正修复

当用户已经指出“目标远未达成却屡次说完成”时，问题通常不是最后一句话太乐观，而是 agent 没有把用户目标、已定方案、真实产物和实现机制绑在一起。只承诺“不再说完成”“以后叫工程侧完成”仍然是表面修复。

应对：

- 回到目标实现门，检查用户要的主效果是否真实出现；
- 找出旧机制、旧 fallback 或弱替代路径是否仍在冒充新方案；
- 对视觉/多模态目标，用最终样张、截图、录屏或用户确认作为主要证据；
- 若证据不足，降级完成等级，并继续修复真正缺口。

## 2. 新方案不能被旧路径补丁冒充

当用户已经要求新机制、新设计或新方案时，在旧绘制函数、旧 fallback 或旧 resolver 上增加装饰，通常只是降低风险的局部补丁，不等于方案落地。

应对：

- 先证明方案经过正确实现路径；
- 如果当前模型表达上限不足，停止低价值修补；
- 明确提出机制升级、素材化、独立 renderer、数据模型迁移或用户决策。

## 3. 测试断言可能奖励错误行为

“尺寸变大”“节点存在”“像素不是空白”“水印出现”可以挡住完全失效，却挡不住“看起来完全不像目标”。弱测试会鼓励 agent 修到测试绿，而不是修到用户目标达成。

应对：

- 为目标设计强证据，而不是只为实现路径设计断言；
- 视觉任务至少需要真实样张/截图/人工判断之一；
- 自动测试只作为回归护栏，不替代产品验收。

## 4. 阶段不同，正确动作不同

用户要求“先给多个方案”时，应该先产出可比较方案并等待选择。用户已经选定方向时，应该停止发散，把方案细化成真实落地，并验证最终产物。

应对：

- 在 Delivery Contract 中标记当前阶段：`selection`、`implementation`、`verification`、`release`；
- 不在 `selection` 阶段过早提交生产补丁；
- 不在 `implementation` 阶段用重新发散逃避落地。

## 5. 收口工具不能替代交付判断

`clean-checkpoint-first` 让工作区可审计，但不能提高交付完成等级。一个干净 commit 也可能只是干净地提交了未达目标的实现。

应对：

- 先用本 skill 判断目标完成等级；
- 再用提交/合入流程收口；
- final response 同时报告 checkpoint 状态和目标验收状态，不能合并成一个“完成”。

## 6. 借鉴已有 skill 要做适配，不做拼贴

`user-value-architect`、`product-sense-refiner`、`abstraction-architect` 都能解释交付失败的一部分，但它们的完整工作流不是本 skill 的目标。盲目吸收会把一个交付门槛变成重型分析编排，反而让 agent 又开始绕开实际落地。

应对：

- 从 `user-value-architect` 只借“用户可感知目标”作为证据门槛；
- 从 `product-sense-refiner` 只借事实、判断、表达分层，防止回复误导；
- 从 `abstraction-architect` 只借旧路径上限和候选升级判断；
- 需要完整分析时只给 handoff，不自动启动或内嵌它们。
