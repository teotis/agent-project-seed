# Goal Delivery Contract

本参考文件用于把「需求需要真实落地但 agent 交付漂移」的任务变成可审查的交付矩阵。同时承载 pre-delivery lens（交付前轻量自检）的自动触发门槛、五维与根因分类规则。

## 0. Pre-Delivery Lens（交付前轻量自检）

pre-delivery lens 只在非例行需求落地风险成立时自动触发，做清零 + 五维自检 + 偏差根因定位。轻量只是少做 Delivery Contract / Gap Ledger 矩阵，不是允许放行偏差：发现偏差不得照常声称完成。

### 0.0 自动触发门槛（Delivery-Risk Moment）

自动触发不是看「有没有产物」或「是否准备 final」，而是看本次交付是否存在明显的需求落地风险。

#### Trigger Calculus

自动触发判定式（任一分支成立即触发）：

```
auto-trigger = explicit_user_invocation
             OR prior-correction-risk
             OR path-substitution-risk
             OR (non-routine_landing
                 AND interpretation-or-complexity
                 AND user-or-downstream_dependency)
```

前三项是 **override risk**：单独成立即触发，不需 AND 三项。最后一项是 **baseline risk**：三项 AND 才触发。

**全局不触发**：用户明确要求快速执行且不需要交付验收判断时，无论判定式结果如何，都不自动触发（见下方「不自动触发」）。

#### 各 term 判定标准

| term | 判定标准 | 正例 | 反例 |
|---|---|---|---|
| `explicit_user_invocation` | 用户显式点名本 skill 或同义触发词 | "用 done-claim-gate 检查" / "用户视角检查一下" | 仅说"做完了吗"未点名 |
| `prior-correction-risk` | 用户已表达不满/纠偏，或指出"目标没达到/还是旧机制/别只说测试通过" | 用户质疑完成声明 | 首次交付无纠偏历史 |
| `path-substitution-risk` | 旧 fallback/旧模板/旧渲染器/旧数据流/旧报告骨架或外部改动可能覆盖新方案 | 仓库已有旧导出模板可能被继续使用 | 全新项目无旧路径 |
| `non-routine_landing` | 需把用户目标落成新行为/结构/界面/报告/接口/导出/发布包/可复用产物；非稳定模板换数据、非明确机械小改 | 迁移方案落地、新导出契约、UI 行为变更 | 精确改名、补一行配置、修 typo、稳定报告换数据 |
| `interpretation-or-complexity` | 用户给宽泛方向需 agent 补判断；**或**用户给明确方案但落地跨多路径/高依赖 | 宽泛产品方向、明确但跨模块的迁移方案 | 单一路径的明确机械小改 |
| `user-or-downstream_dependency` | 产物影响用户操作/判断/发布/复用/集成/自动化消费/后续决策 | 下游脚本消费的 CLI 导出 | 内部重构不改外部契约 |

#### 边界明确

- 明确机械小改（精确改名/补一行配置/修 typo）→ `non-routine_landing` 不成立 → 不触发。
- 明确但复杂的落地（迁移、UI 行为、导出契约、跨模块方案）→ `interpretation-or-complexity` 成立（复杂落地分支）→ 触发。
- 宽泛但低影响的小文案润色 → `user-or-downstream_dependency` 不成立 → 不触发。

#### 不自动触发

- 例行模板/固定流程运行，例如稳定报告换数据、固定导出、同步、清理、状态查询；
- 用户给出明确机械小改，例如精确改名、按指定文案替换、修 typo、补一行配置；
- 低影响文案润色、普通 final 摘要、命令输出转述；
- 内部重构或维护不改变用户/下游可见契约；
- 用户明确要求快速执行且不需要交付验收判断。

### 0.1 清零（Zero-Context Reset）

自检前显式放下三类上下文污染：

- 放下「我已做完」心态：不把代码写了 / 测试绿了 / 构建成功 / 已提交当作用户目标达成的证据。
- 放下「规格满足」心态：规格是 proxy，不是用户真实目标。
- 放下「过往路径惯性」：产物里有旧 fallback / 旧渲染器 / 旧状态机时，不默认它是对的。

产出一句零基锚点：「用户拿到这个产物，能达成什么真实目标」。

零基锚点必须标注 **目标来源**：

| 来源 | 判定 | 对完成声明的影响 |
|---|---|---|
| `用户原话` | 用户在当前或近期会话中明确说出的目标 | 可按正常完成等级声明 |
| `可靠推断` | 从至少 2 个独立明确信号交叉推出的目标，且无反证 | 可按正常完成等级声明 |
| `agent 推断` | agent 单方面从上下文推断，用户未明确确认 | 完成声明上限为 `engineering-complete`，不能说 `complete`（见第 7 节） |

`可靠推断` 的独立信号可以来自用户原话中的不同约束、已选方案、下游消费契约、验收证据要求、用户纠偏历史或当前任务路径。不能把同一个信号换种说法重复计数；只有 1 个信号、存在反证、或需要 agent 自行补全关键目标时，标为 `agent 推断`，并按完成声明上限处理。

### 0.2 五维自检

固定 5 个维度，每维给出明确判断，不得跳过：

| 维度 | 要问 | 判断值 | 证据反模式 |
|---|---|---|---|
| 目标触达 | 用户真正目标是什么（按 0.1 标注的目标来源）？产物触达目标了吗，还是只满足表面规格？**若目标来源是 `agent 推断`，先确认目标本身是否成立，再判断触达。** | 触达 / 表面规格 / 未触达 | 只新增按钮但关键流程不可用；只生成报告文件但没有回答用户要做的判断；只改接口字段但下游仍拿不到新语义；agent 自造一个合理目标然后宣称触达 |
| 用户操作视角 | 从用户实际操作或下游消费看，有无明显不可用 / 低效 / 误解？入口是否直观，默认路径是否贴近意图，操作数、判断数、上下文重建和恢复成本是否合理？ | 无明显问题 / 具体问题 | 工作流需要反复手动补救；CLI 输出缺少可复制的下一步；长报告无目录无锚点；导出格式让自动化消费困难；强能力藏在需要记隐藏规则或多步手工串联的高级路径里 |
| 决策可用性 | 用户能否区分这个产物的用途、差异、场景和可信边界？ | 清晰 / 模糊点 | 两个导出按钮命名让用户无法区分差异；报告结论没有区分事实、判断和建议；API 变更说明没有说明兼容性影响 |
| 真实场景深度 | 内容是真实场景还是模板化套话？证据是否足够支撑用户使用？ | 真实 / 套话 | 架构建议只有抽象口号没有代码路径；迁移计划没有失败回滚边界；产品文案只描述功能不覆盖实际使用阻力 |
| 路径真实性 | 产物是否落在真实路径上，还是旧 fallback / 被覆盖的好改动？ | 真实路径 / 旧路径陷阱 | 新交互只改了 demo 未进真实页面；导出仍走旧模板；外部 agent 改动覆盖好改动未恢复；测试覆盖新函数但运行时仍走旧路径 |

### 0.3 偏差根因分类

偏差是症状，根因是「什么上下文让我瞄准偏了」。三类根因：

| 根因类型 | 定义 | 识别信号 |
|---|---|---|
| `context-contamination` | 被旧方案、旧规格、旧 fallback、过往对话惯性、技术术语带偏 | 产物里有旧 fallback / 旧渲染器；命名用技术术语非用户语言；套用过往模板；规格满足但目标未触达且规格来自旧对话 |
| `flow-misfit` | 流程顺序错误，如先实现后想目标、跳过用户场景验证 | 没问「用户拿这个做什么」就实现；从数据结构而非操作流程设计；跳过真实场景调研从模板生成；交付前没做用户视角自检 |
| `legacy-rule-drift` | 过往路径规则不当，如外部改动覆盖好改动、旧约定未更新 | 好改动被外部覆盖未恢复；旧约定仍生效但已不适用；沿用旧交互模式未随场景演进；产物路径与已定方案不一致 |

### 0.4 偏差处置

- 偏差影响完成声明 → 升级到 completion claim gate（第 1-8 节）。
- 偏差不影响完成声明但影响交付质量 → 输出偏差摘要并建议修正，修正后交付。
- 无偏差 → 输出 pass 摘要即可，不强制造问题。

#### 偏差影响完成声明的判定

pre-delivery lens 发现偏差后，按下表判定是否必须升级。任一 `must-upgrade` 条件成立，就不能继续使用 `complete/达标/已解决` 口径，必须进入 completion claim gate 或先修正偏差。

| 偏差类型 | must-upgrade 条件 | 可不升级的条件 |
|---|---|---|
| 目标触达 | 产物只满足表面规格、目标来源为 `agent 推断` 却准备说 `complete`、或核心用户目标没有验收证据 | 只是低风险表达瑕疵，且目标已由用户原话/可靠推断确认并有真实证据 |
| 用户操作视角 | 用户/下游无法完成关键操作、输出不可消费、需要未说明的手工补救、必须记隐藏规则、操作/判断/上下文重建成本明显偏高，或强能力不可从默认路径到达 | 只影响易读性/便利性，且已给出明确修正或不影响当前验收 |
| 决策可用性 | 结论、取舍、兼容边界或风险会误导用户做错判断 | 仅缺少次要背景，不改变当前完成等级 |
| 真实场景深度 | 交付物是模板化套话、缺少真实路径/真实样张/真实数据，且这些证据是目标成立条件 | 只是辅助例子不足，核心证据仍能支撑目标 |
| 路径真实性 | 实现仍走旧 fallback/旧模板/旧渲染器/旧导出路径，或无法证明新方案进入最终路径 | 旧路径明确不参与最终产物，且已有反证或运行证据 |

输出时必须给出一句 `升级判定`：`must-upgrade` / `repair-before-final` / `safe-to-summarize`，并说明触发的维度。`safe-to-summarize` 只允许在偏差不改变完成等级且已有替代证据时使用。

偏差需跨会话积累时，记录到 memory（若 `engineering-memory` 可用）：

```text
偏差事件:
- 时间: <timestamp>
- 产物: <产物类型与路径>
- 偏差维度: <目标触达 / 用户操作视角 / 决策可用性 / 真实场景深度 / 路径真实性>
- 根因类型: <context-contamination / flow-misfit / legacy-rule-drift>
- 具体描述: <偏差内容>
- 建议修正: <修正方向>
- 是否 pattern: <单次 / 跨会话同类第 N 次>
```

单次偏差是事件，跨会话同类偏差（同一维度 + 同一根因，2+ 次）是 pattern。pattern 达阈值时建议用户显式调用 `user-value-architect`，不自行升级。

## 1. Delivery Contract

先抽取以下字段。能从用户上下文可靠推断时不要打断用户；缺失字段会改变实现方向时，只问一个阻塞问题。

| field | question |
|---|---|
| `user_goal` | 用户真正要达成什么结果？**必须标注目标来源**（`用户原话` / `可靠推断` / `agent 推断`，判定标准见 0.1 节）。`agent 推断` 目标的完成声明上限为 `engineering-complete`（见第 7 节）。 |
| `fixed_plan` | 哪个产品/设计/技术方案已经被选定？ |
| `must_preserve` | 哪些气质、行为、路径、数据、兼容性或约束不能被替代？ |
| `not_enough` | 哪些工程证据不能单独证明完成？ |
| `acceptance_evidence` | 需要什么真实产物、截图、样张、日志、测试、APK/source alignment 或用户确认？ |
| `external_gate` | 哪些验收必须由真机、账号、人工视觉判断、用户确认或发布审批完成？ |
| `operation_model` | 用户或下游实际如何进入、理解、执行和恢复？是否需要额外记忆规则、多步手工串联或上下文重建？ |

## 2. Goal Realization Gate

这是本 skill 的核心门槛：判断目标是否真实实现，而不是判断回复措辞是否足够谨慎。

当用户质疑“目标远未达成却说完成”时，先回答四个问题：

| question | pass condition | fail signal |
|---|---|---|
| 目标是否仍是用户原目标？ | 输出直接对应用户指定的设计、效果、行为或发布结果 | 把目标降级成“有水印”“有 UI”“有测试”“有 commit” |
| 方案是否走了正确机制？ | 已定新方案触达最终运行/渲染/输出路径 | 继续在旧绘制函数、旧 fallback、旧 resolver 或弱替代路径上补装饰 |
| 证据是否来自最终产物？ | 样张、截图、录屏、真实文件、APK/source alignment、设备流程或用户确认能支撑目标 | 只拿中间对象、mock、单测、构建结果或存在性检查当证据 |
| 缺口是否改变完成等级？ | 缺口被记录并使声明降级到 `engineering-complete`、`partial`、`blocked` 或 `not-complete` | 最终表达仍让用户以为目标已经达成 |

视觉/多模态任务的额外要求：

- 必须查看或生成用户最终会看到的图像、视频、预览、最终样张或截图；
- 若无法视觉核验，标记 `visual_evidence_unavailable`，不得宣称“设计达标”；
- 若用户已经说“看起来不像设计图/不像目标效果”，优先检查实现机制是否错位，而不是继续微调旧参数；
- 如果当前技术路径表达上限不足，输出机制升级或 blocked decision，而不是把低价值修补包装成完成。

人类终端适配性的额外要求：

- 对用户可见或下游消费产物，必须检查入口、默认路径、操作数、判断数、上下文重建和失败恢复成本；
- 若关键目标需要用户记隐藏规则、执行未说明的多步手工补救、在多个输出之间自行转译，或能力只存在于非直观高级路径，完成等级最高为 `engineering-complete`，除非用户明确接受该操作模型；
- 说明文字只能降低误解，不能替代直观路径。若只能靠长说明才能完成主目标，应标记为用户操作视角偏差。

## 3. Plan-To-Implementation Map

把已定方案拆成可验证义务，而不是直接跳进现有函数补丁。

| plan item | implementation obligation | verification obligation | status |
|---|---|---|---|
| 用户可见主效果 | 必须触达最终渲染/输出/发布路径 | 最终产物可见，而不是只在预览或测试 fixture 可见 | `done/partial/not-done/blocked` |
| 新机制/新方案 | 必须经过新路径或明确升级后的路径 | 证明没有退回旧 fallback、旧 resolver、旧 renderer、旧 default | `done/partial/not-done/blocked` |
| 关键体验判断 | 必须保留用户要求的风格、语义或交互结果 | 样张、截图、录屏、真机或用户确认 | `done/partial/not-done/blocked` |
| 工程闭环 | 测试、构建、提交、APK/source alignment | 只证明工程可交付，不自动证明目标达成 | `done/partial/not-done/blocked` |

### 旧路径陷阱

遇到这些信号时，必须停下来证明方案路径正确：

- 用户说“明明已经设计了新方案，但看起来还是旧的”；
- 当前实现只改了已有 fallback、装饰函数、文案或参数；
- 预览/设置页有效，但最终产物无效或弱化；
- 测试只检查存在、尺寸、编译、节点创建，没有检查目标效果；
- agent 计划用“更深颜色、更多线条、更多断言”替代用户要求的新方案；
- 构建、APK 或 commit 已完成，但真实输出尚未核验。

## 4. Borrowing Filter

参考已有 skill 时只吸收适配本任务的局部机制。不得把下游 skill 的完整工作流、报告格式、预算档位或自动调用权限搬进本 skill。

| source skill | borrow when | borrow only | do not borrow |
|---|---|---|---|
| `user-value-architect` | 目标是否达成取决于用户可感知价值、信任、默认体验或主效果 | `User-Perceived Value Gate`：用户最终看到/感受到的结果是否支持目标；把不可见工程整洁降级为辅助证据 | 不启动 Deep Value Analysis；不重新发散高上限候选；不把已定方案改写成新产品方向 |
| `product-sense-refiner` | agent 可能把事实证据写成判断结论、默认回复会误导用户，或目标是否达成取决于入口、默认路径、操作数、上下文负担或能力可达性 | `Fact / Judgment / Expression`：事实是测试/构建/截图，判断是完成等级，表达是最终回复措辞；`Human Terminal Fit`：用户是否能用少而直观的操作达成目标，强能力是否进入默认可达路径 | 不重做产品方案；不加入评分、排名、推荐框架或完整产品报告；不把交付验收扩成新一轮产品探索 |
| `abstraction-architect` | 用户指出新方案仍像旧机制，或当前实现模型表达上限不足 | `Mechanism Ceiling Gate`：低抽象基线、旧路径反证、候选升级条件、可证伪测试 | 不生成完整架构报告；不默认寻找宏大抽象；不未经授权实施迁移或重构 |

### Adaptation Rules

- 先看触发信号，再借机制；没有触发信号时不借。
- 借来的机制必须服务于完成声明权限，而不是扩大分析范围。
- 如果借鉴会让 agent 停止交付、重新发散或隐藏当前缺口，拒绝借鉴。
- 如果当前任务已经需要完整价值分析、产品重构或结构抽象报告，只输出 handoff 建议，等待用户授权调用对应 skill。
- 每次实际借鉴后都要写入 `Borrowing Absorption Check`：借了哪个局部机制、它落在 Delivery Contract / Goal Realization Gate / Gap Ledger / Completion Claim Permission 的哪一项、它是否改变完成等级。若借鉴机制没有落到这些输出之一，视为未吸收，删除该借鉴或改成 handoff。

## 5. Evidence Matrix

用证据类型匹配目标，不把低层证据抬高成高层结论。

| target type | strong evidence | weak evidence |
|---|---|---|
| 视觉/设计主效果 | 真实样张、截图、对照图、用户确认、像素/视觉回归加人工判断；并能说明用户可感知目标如何达成 | 单测绿、颜色常量变更、预览层截图 |
| 最终输出/成片 | 最终文件、真实后处理路径、artifact hash、metadata/source alignment | 中间 bitmap、mock、resolver 单测 |
| 关键交互 | 录屏、UI 自动化、真实设备流程、可复现步骤 | ViewModel 单测、截图静态存在 |
| 架构/机制切换 | 新路径被调用、旧 fallback 被绕开或删除、接口/数据流证据；旧模型表达上限已被反证或新路径必要性已证明 | 在旧函数里新增分支或注释 |
| 发布/交付包 | APK/包路径、SHA、source alignment、发布前审批状态 | 构建成功、版本号变化 |

## 6. Gap Ledger

每个关键目标项必须落入以下之一：

- `done`：实现映射和目标匹配证据都存在；
- `engineering-done`：代码、测试或构建完成，但用户可见目标仍缺真实验收；
- `partial`：只覆盖部分方案，或证据不足以支持整体目标；
- `blocked`：需要用户、设备、账号、素材、审批或外部环境；
- `not-done`：目标项尚未实现。

记录格式：

```text
目标项:
当前状态:
实现证据:
验收证据:
缺口/反证:
下一步:
```

## 7. Completion Claim Permission

最终回复只能使用与证据相称的完成等级。

| level | allowed wording | required condition |
|---|---|---|
| `complete` | “已完成/已达成” | 所有关键目标 `done`，外部验收已完成或用户明确授权无需等待；**且目标来源非 `agent 推断`**（`agent 推断` 目标上限为 `engineering-complete`；若用户在交付前显式确认该目标，来源升级为 `用户原话`，按正常等级声明） |
| `engineering-complete` | “工程侧已完成，待真实验收/用户确认” | 代码、测试、构建或包齐全，但真实目标仍需外部验收 |
| `partial` | “已完成其中 X，Y 仍未完成” | 部分关键目标缺实现或证据 |
| `blocked` | “当前被 X 阻塞，不能宣称完成” | 缺不可替代输入、设备、账号、审批或用户判断 |
| `not-complete` | “尚未完成” | 核心方案未落地、走错路径或证据反向 |

禁止口径：

- 用“测试通过”直接推出“需求完成”；
- 用“有水印/有 UI/有节点”直接推出“设计达标”；
- 用“本地 commit/API 返回成功/生成 APK”直接推出“用户目标已实现”；
- 把“后续需要用户确认”的任务写成“已经闭环”。
- 用 agent 自造目标（未与用户确认）满足后宣称 `complete`；`agent 推断` 目标最多 `engineering-complete`。

### Fact / Judgment / Expression Check

最终回复前做一次三层拆分：

| layer | example | rule |
|---|---|---|
| Fact | 已修改文件、测试命令、截图、样张、APK SHA、设备结果 | 只能陈述观察到的证据 |
| Judgment | `complete`、`engineering-complete`、`partial`、`blocked`、`not-complete` | 必须由 Evidence Matrix 和 Gap Ledger 推出 |
| Expression | “工程侧已完成，视觉仍待真机确认” | 必须让用户不会误解为目标已完全达成 |

如果表达比判断更乐观，降级表达；如果判断比事实更乐观，降级判断。
