# Problem Package Contract

## Purpose

问题包是修复方案设计之前的上游分析工件。它描述“发生了什么、可能涉及哪里、为什么这些问题适合一起继续核查”，但不宣称已经完成根因证明或实施设计。

## Document Template

```markdown
# 批量问题初查与问题分包

## 核查摘要

- 输入问题数：
- 问题包数：
- 已查看证据：
- 未查看或不可用证据：
- 总体限制：

## 输入覆盖

- [x] ISSUE-001：原始问题简述
- [x] ISSUE-002：原始问题简述

## 分包总览

| 问题包 | 包含问题 | 领域 | 复杂度 | 置信度 | 当前判断 |
|---|---|---|---|---|---|

## PKG-01 包标题

- **包含问题**: ISSUE-001, ISSUE-002
- **领域**: UI / Camera Session / Media / Settings / Mode Plugin / Device
- **修复复杂度**: S / M / L / XL
- **初查置信度**: 高 / 中 / 低
- **当前判断**: 已确认 / 高可能 / 待核查 / 信息不足
- **建议优先级**: P0 / P1 / P2 / P3

### 问题表现

逐项描述用户能看到或复现的行为。包含触发条件、界面/模式、时序、预期行为和实际行为。

### 用户影响

说明功能不可用、误导、构图困难、性能退化、数据风险或体验成本。

### 初步分析

写出共享根因候选、关联模块和为什么适合合包。不得把候选写成定论。

### 证据与未知

- 观察事实：
- 当前代码或测试证据：
- 反证或替代解释：
- 待补证据：

### 范围与依赖

- 可能所有权：
- 前置依赖：
- 关联包：
- 明确排除：

### 后续细化重点

列出下游 planner 应核查的调用链、状态、兼容性、验证矩阵和修复方案选择点。

## 跨包关系与建议顺序

说明共享基础设施、阻塞关系、可并行关系和需要先证伪的假设。

## 推荐使用方法

在新 agent 窗口输入：

`/agent-orchestration-planner 针对如下外部 agent 已经初步分析的问题集合，进行核查确认，设计细化修复方案，制作好任务包。`

然后粘贴一个完整问题包。下游 agent 应重新核查事实，不直接继承初步根因判断。
```

## Writing Rules

- “问题表现”必须是用户可观察描述，不能只写模块名或抽象结论。
- “初步分析”至少包含一个根因候选；证据不足时明确写低置信度。
- 多个问题合包必须说明共同修复路径。只有视觉上相邻不是充分理由。
- 对跨包问题指定一个主包，并在其他包写“关联”，避免重复所有权。
- 优先级根据用户影响、阻塞性与风险确定，不根据实现难度单独确定。
- 下游细化重点写调查问题和决策点，不提前伪造具体代码改法。
