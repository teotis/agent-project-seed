# Problem Package Contract

## Purpose

问题包是修复设计之前的决策工件。它描述发生了什么、哪些证据支撑当前判断、这些问题是否值得修复、为什么应共同处理，以及下一步应进入哪条路径，但不宣称已经完成根因证明或实施设计。

## Grouping Rules

- 优先形成共享修改边界和共享验证边界的依赖闭包。
- 大包不是失败；切断真实依赖、制造跨包双向协调才是失败。
- 只有通过稳定接口连接、可独立验收、可独立验证、可独立回滚和落地时才拆包。
- 跨包依赖应尽量单向，并明确主依赖方向。
- 视觉上相邻、编号相邻、数量均匀或领域标签相同，都不是充分合包理由。

## Routing Rules

- `diagnosing-bugs`：仍需深度根因诊断。
- `handoff`：单包或少量清晰任务，可轻量交接。
- `orchestration`：多包依赖、并行执行、持久状态、恢复或最终收口。
- `external-assist`：设备、账号、凭证、审批或人工判断。
- `deferred`：证据、价值或时机不足。

`orchestration` 必须写出具体编排理由；问题数量多、单包大或实现复杂本身不是充分理由。

## Fix-Worthiness Rules

- `fix-now`：用户影响明确，行为与产品目标、验收标准或已承诺能力冲突，证据足以进入修复或交接。
- `worth-fixing-needs-evidence`：问题看起来值得修，但缺少复现、日志、设备、账号、视觉判断或范围证据。
- `needs-user-decision`：是否修复取决于产品取舍、兼容策略、发布节奏、设计偏好或成本上限。
- `defer`：影响较低、证据不足、重复度高、时机不合适或依赖上游变化，当前不应投入修复。
- `no-fix`：核查后确认是预期行为、误报、外部限制、不可支持场景，或修复会破坏更重要的不变量。

不得因为实现困难直接判定不值得修；复杂但高影响的问题应暴露为用户决策或编排需求。不得因为证据不足直接判定 `no-fix`；证据不足只能降低置信度、改为补证据或延期。

## Writing Rules

- “问题表现”必须是用户可观察描述，不能只写模块名或抽象结论。
- 所有主要判断必须引用 Evidence ID。
- “修复价值核查”必须说明用户影响、规范冲突、证据强度、修复风险或机会成本。
- “初步分析”至少包含一个候选解释；证据不足时明确降低置信度。
- 优先级根据用户影响、阻塞性与风险确定，不根据实现难度单独确定。
- 下游细化重点写调查问题和决策点，不提前伪造具体代码改法。
